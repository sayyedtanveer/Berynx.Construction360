# P1-M06 Sales Orders

## Scope and status

This change adds the implementable M06 order lifecycle and its M04/M05 handoff. It does not implement M07 purchase orders, M08 dispatch, M10 billing, or M11 receipts. The live database was not accessed. Builds, automated tests, and EF migration generation could not be run because `dotnet`, `node`, and `npm` are unavailable in the selected local checkout's command environment.

The manual PostgreSQL package is present under `database/scripts/P1-M06/`. **The EF Core migration source and model snapshot are still pending**: the package deliberately does not write a guessed row to `__EFMigrationsHistory`. Do not deploy this SQL package as a substitute for the normal reviewed migration workflow until that gap is closed.

## Backend/API and domain

Route group: `/api/v1/m06`

- `GET /orders`, `GET /orders/{id}`
- `POST /orders`, `POST /orders/from-quotation/{quotationId}`
- `POST /orders/{id}/confirm`, `/schedules`, `/hold`, `/cancel`, `/short-close`, `/reverse-short-close`
- `POST /orders/{id}/amendments`, `/amendments/{amendmentId}/apply`
- `GET /orders/{id}/confirmation`, `GET /reports/pending-orders`
- `GET/PUT /settings/delivery-tolerances`

Core entities in `Berynx.Domain.SalesOrders`: `M06SalesOrder`, `M06SalesOrderLine`, `M06SalesOrderCharge`, `M06QuotationAllocation`, `M06QuotationChargeAllocation`, `M06DeliverySchedule`, `M06Amendment`, `M06Activity`, and `M06LinkedDocument`. `M06Rules` owns the allowed lifecycle transitions and tolerance calculation.

The `Berynx.Application.SalesOrders` records define read-only future handoff contracts for M07 purchase requests, M08 delivery facts, M10 billing eligibility, and M11 payment progress. They do not imply that those modules are operational.

## M04/M05 quotation handoff

- M06 accepts only `Accepted`, unexpired M05 quotations and checks both M05 viewing scope and M06 creation scope.
- Conversion is transactional/serializable, idempotent by tenant key, and records line-level quantity allocations. Per-line request quantities cannot exceed remaining accepted-quote quantities.
- Quote charges are apportioned against the remaining quote-line value and persisted as separate charge allocations to avoid duplicating the full quote charge on each call-off.
- M05 quote detail now exposes consumed/remaining quantity and the orders created from the quote. The M06 form preloads those remaining quantities.
- When an order originates from an M04 enquiry, conversion links the persisted M06 order to the enquiry, marks it Won, and records M04 activity/audit in the same transaction.
- A quote with an already-Won or Lost enquiry cannot be converted through the M04 linkage flow. Review legacy enquiries requiring conversion before deployment.

## Credit, margin, access and licensing

- M06 routes require the M06 module entitlement. Write endpoints request write-enabled module access, so suspended tenants remain read-only.
- Server permission codes include view/create/edit/confirm/approve/cancel/schedule/amend/report/export/print, hold, short-close reversal, rate override and delivery-tolerance configuration. Branch, plant and own-data scopes are checked server-side.
- Purchase-cost/margin values are not returned in order detail or exports without `global.view_cost`; no margin value is synthesized.
- The optional `M06` PlatformModule and permissions are registered by `04-seed.sql`. No plan module or tenant entitlement is automatically granted.
- Exact test-tenant activation steps are in `database/scripts/P1-M06/README.md`: PlatformAdmin reassigns the tenant's current plan and preserves all existing add-ons while adding `M06`.
