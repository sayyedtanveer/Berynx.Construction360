# P1-M10 Sales Invoicing — implementation checkpoint

**Status: PARTIAL.** Draft and transaction-aware posting source are implemented, but M18 provider-backed evidence and database verification remain blockers. Not complete or UAT-ready. Requirements are in `docs/requirements/BRD_v2.2.md` (US-M10-01 through US-M10-13; BR-M10-01 through BR-M10-15).

## Implemented source

- Tenant/module/RBAC-protected API and Angular route `/m10/invoices`.
- Draft creation from selected M09 challans only when status is `Delivered` and evidence is `Verified`; server validates one branch/customer/site, branch scope, frozen M06 rates, delivered-minus-invoiced quantity, place-of-supply state and unique challan reservation.
- Draft totals use decimal arithmetic, branch-vs-site state to choose CGST+SGST/IGST, nearest-rupee draft round-off and an idempotency key.
- Draft detail and cancellation preserve event history and release challenged rows. Posting revalidates delivery facts and calls the existing M12 engine within the invoice transaction; persisted posting/reconciliation remains database-unverified.
- Draft generation is blocked when M08 trip waiting/part-load charges are present, avoiding silent underbilling.

## Critical integration boundary

M08 now has an authorized no-OTP evidence review path, and M09 derives challan status from persisted review facts. Without the configured M18 secure storage/scanning provider, submitted references cannot be reviewed, so new challans remain `Unverified` and M10 correctly returns no invoice-eligible challans. The application does not fabricate a successful invoice.

## Posted invoice cancellation slice — 2026-11-27

**Source implementation: PARTIAL; PostgreSQL persistence and authorized-handler execution remain PENDING.** BR-M10-06 and US-M10-09 now have an M10 cancellation route and UI action for a posted invoice when no M11 receipt allocations exist and no IRN is present. The endpoint requires the existing `m10.invoices.post` authorization and a non-empty reason, checks invoice version and branch scope, then uses one serializable transaction to:

- construct exact debit/credit mirror lines from the immutable original M12 voucher and post them through `IM12PostingEngine`;
- link the reversal with `M12Voucher.ReversalOfVoucherId` and a unique tenant-scoped constraint;
- mark the invoice `Cancelled`, retain the original invoice/voucher history, and record the reason and reversal voucher in M10/M09 events;
- release challan reservations, clear their active invoice link and restore the source M06 order lines' invoiced quantities.

Cancellation fails closed if the invoice has a receipt allocation, an IRN, no valid original M10 voucher, missing invoice/challan/order-line facts, or an unreconciled original voucher. An invoice with an IRN needs portal cancellation acknowledgement first; that workflow is not implemented. Receipt unallocation is also not implemented, so allocated invoices cannot be cancelled via this endpoint. The exact reasons, reversal construction and Angular request/response refresh are covered by domain and UI contract tests; **the authorized endpoint handler has not been executed with PostgreSQL**.
