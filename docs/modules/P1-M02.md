All screens use Angular forms and responsive layouts with labels, focus-visible states, loading, empty, success and error messages. API authorization remains authoritative.

The public auth component is separate from the authenticated Carbon & Copper shell. `/login` is the only public login route; invitation and password-reset return URLs must target `/login`. Public account creation is not enabled by the existing product policy/configuration, so the login page directs company-workspace requests to a PlatformAdmin instead of exposing a public tenant-creation API. Employee self-registration is not offered. The local Development reset link, when explicitly enabled, remains a signed, one-time Identity reset-token URL; there is no public arbitrary-account reset endpoint. Sensitive reset/invitation query tokens are removed from the browser URL after being captured in memory.

The authenticated header obtains the tenant/user display context and tenant-filtered in-app notifications from M02 APIs. Logout revokes the server session before clearing the local token (and clears local state if the API is unavailable). Sidebar Access Control entries and Users/Add User controls are permission-filtered for usability; server-side RBAC and tenant isolation remain the security boundary.

## Backend design

- **Domain:** tenant-owned memberships, roles, scoped assignments, approval rules/levels/requests/decisions, delegations, audit events, notifications, authentication challenges, sessions and refresh-token records.
- **Application contracts:** `IM02InvitationDeliveryProvider`, `IM02Access`, `IM02ApprovalEngine` and `IM02TaskReassignmentProvider`. ASP.NET Core Identity is the sole local credential/token authority; the configured external service is for email delivery only.
- **Infrastructure:** EF Core mappings, current-tenant query filters, write-boundary checks, manual-deployment migration model, system-role bootstrap, approval submission and PostgreSQL constraints/triggers.
- **API:** `/api/v1/m02/*`, anonymous local `/api/v1/m02/auth/*` credential, challenge, refresh and password endpoints, and authenticated `/api/v1/auth/session`. Refresh tokens are stored hashed, rotated once, and delivered in an HttpOnly, Secure, SameSite=Strict cookie. Auth endpoints have an IP fixed-window rate limit. M02 endpoints require validated `sub`, `tenant_id`, `user_id`, and active `sid` claims plus server-side permission checks. Invalid authentication returns 401; authenticated authorization failures return 403.
- **First-load session behavior:** Angular stores only a non-secret refresh-availability hint in local storage; it never reads the HttpOnly cookie. Without that hint, Angular calls anonymous `GET /api/v1/m02/auth/refresh-state`, which returns only whether the server received the HttpOnly refresh cookie (and is `no-store`). A missing cookie means no refresh request. An existing cookie permits one deduplicated silent refresh and server session check, including cookies created before the local hint existed. Failed refresh clears local state and expires the cookie; the bearer interceptor retries a protected request once and sends the user to login if refresh fails. Protected routes include `/` and every M01–M03 route.
- **Platform administrator:** `M02AuthenticationService` adds `PlatformAdmin` only for Identity IDs in trusted server configuration (`PlatformAdmin:IdentityUserIds`). A tenant role or browser claim cannot grant the global role. The local development provisioner prints the identity ID to configure; do not commit it. This current tenant-scoped session architecture requires the platform operator to have an active tenant membership.
- **Key security rules:** permission grants are unions across assigned roles; there is no implicit role inheritance. `All`, `Branch`, `Plant` and `Own` scopes are combined as a union for a permission. A role assigner must hold each granted permission at the assigned scope. Approval submissions carry branch, plant and record-owner scope so inbox, decisions and cost visibility can be checked against the specific source. Current tenant always comes from the trusted JWT tenant context.
- **Concurrency:** version tokens on users, custom roles, approval rules and approval requests; unique pending source constraint; database locking/trigger for last-admin invariant; immutable source snapshots/conditions, decisions and audit records.
- **Approval integration:** business modules submit a source ID, typed conditions and immutable JSON snapshot through `IM02ApprovalEngine`. A changed pending snapshot cancels/audits the old request and creates a new one. A module must call this contract on every relevant source edit.

### Local development login fixture

`database/scripts/DEV-AUTH/README.md` documents the manual M01–M03 migration/seed order and the four `DEV-AUTH` SQL files. Those scripts add development role templates and create one labelled tenant/branch only when there are no tenants; they never write Identity password hashes. Run `dotnet run --project backend/tools/Berynx.DevAuthProvisioner/Berynx.DevAuthProvisioner.csproj --configuration Release` only after setting `ASPNETCORE_ENVIRONMENT=Development`, the explicit `BERYNX_ENABLE_DEV_AUTH_PROVISIONING=1` flag, and a verified tenant ID. The tool refuses non-local hosts and any database other than `berynx_construction_dev`; it prompts without echo for connection string/passwords, uses `UserManager`, and ordinary provisioning does not reset existing passwords or run migrations. For local Forgot Password UI testing without an email provider, enable `BERYNX_ENABLE_LOCAL_PASSWORD_RESET=1` only on a loopback Development API; a reset link is returned only for confirmed `@berynx.local` accounts. For direct local resets, use the separate explicit `--reset-password <fixture-email>` console mode documented in the DEV-AUTH README; it updates the Identity password through `UserManager`, revokes sessions, and audits the action.
